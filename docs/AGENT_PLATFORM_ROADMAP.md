# Дорожная карта: полный каталог Abacus.ai в Lumenza (2026-08-03)

Контекст: пользователь прислал полный каталог Abacus.ai (150+ пунктов,
13 разделов: App & APIs, Agent Swarms, PowerPoint, Browser Use, Code,
AI Workflows, Videos, Data Analyzing, Trading, Research, Chatbots, Audio)
и явно потребовал реализовать **всё** как полноценный рабочий продукт —
без заглушек и фейковых возможностей. Полный честный разбор всех 13
разделов (что уже покрыто, что дублирует существующие функции, что
требует новой инфраструктуры) записан в памяти проекта
(`project_redesign_initiative.md`, обновление раунда 6) — здесь только
итог и план по шести блокам, которые реально требуют нового движка/
инфраструктуры.

Три параллельных исследования кодовой базы (agent Explore, 2026-08-03)
подтвердили конкретными файлами и строками, что у этих шести блоков
**сейчас нет вообще никакой базы** — это не "расширить существующий
паттерн", а построить с нуля:

## Блок 1 — OAuth/хранение учётных данных сторонних сервисов

Затрагивает: интеграции Code (открыть PR/закоммитить), большую часть
AI Workflows (Slack/Gmail/Jira/Salesforce).

**Что есть сейчас**: единственный прецедент "подключить внешний аккаунт" —
привязка Telegram (`backend/accounts/views.py:169-224`,
`backend/bot/telegram_auth.py`) — работает через один статичный
общий bot-токен приложения + HMAC-подпись payload. Никогда не требовалось
хранить/шифровать/обновлять токен конкретного пользователя. В
`requirements.txt` нет ни одной OAuth-библиотеки (`requests-oauthlib`/
`authlib`/`django-allauth`), нет пакета шифрования на уровне поля
(`django-cryptography`/Fernet).

**Что нужно построить**: полный OAuth2-флоу, модель токена на пользователя
(`access_token`/`refresh_token`/`expires_at`/`scope`), шифрование в покое,
логику обновления/отзыва токена.

**Дополнительно**: перед началом работы над каждой интеграцией пользователю
нужно самому зарегистрировать OAuth-приложение у конкретного провайдера
(Slack app manifest, Google Cloud OAuth consent screen, Atlassian/
Salesforce/GitHub App) и получить `client_id`/`client_secret` — это
внешнее действие, которое не может выполнить сессия с кодом. У некоторых
провайдеров (особенно Google) есть процесс ревью production-scope,
который занимает реальное календарное время.

## Блок 2 — Хостинг сгенерированных приложений/сайтов

Затрагивает: билдер полноценных сайтов/приложений/игр (App & APIs, ~44
пункта).

**Что есть сейчас**: нет S3/CDN (`STORAGES` в `settings.py` — только
`FileSystemStorage`), нет reverse proxy или роутинга по поддоменам, нет
CI/CD в репозитории, нет Procfile/Railway/Render/Fly-конфига. Единственный
переиспользуемый прецедент — self-hosted Piston-песочница в
`code_interpreter/piston_adapter.py`, доказывающая, что команда умеет
запускать недоверенный код в изолированном контейнере — но она рассчитана
на один скрипт до 10 секунд (`RUN_TIMEOUT_MS = 10_000`), без портов и
персистентности — принципиально другая задача, чем раздача живого
многостраничного сайта.

**Что нужно построить**: объектное хранилище или сервис статического
хостинга, слой роутинга/ingress для поддоменов на пользователя, рантайм
сборки (статический экспорт или контейнер на сгенерированное приложение),
решение по биллингу хостинга (это не разовое списание кредитов, а
постоянные расходы на артефакт пользователя).

## Блок 3 — Параллельная оркестрация нескольких агентов (Agent Swarms)

Затрагивает: раздел Agent Swarms (13 пунктов).

**Что есть сейчас**: `agents/tasks.py`'s `run_agent`/`_run_agent_steps` —
строго последовательный цикл `for step in workflow_steps`; поиск по всему
репозиторию `celery.canvas`/`chord(`/`group(`/`chain(` не дал ни одного
совпадения — Celery используется только как обычный `shared_task`+
`.delay()`. У `AgentRun` нет self-relation родитель/потомок. Concurrency
воркера не настроена (нет `CELERY_WORKER_CONCURRENCY`, один `worker` в
`docker-compose.yml` без флага `--concurrency`) — не рассчитана на
реальную параллельную нагрузку.

**Что нужно построить**: задачу-оркестратор на `chord`/`group`, модель
`SwarmRun` с дочерними `AgentRun` через FK, шаг синтеза по завершении
chord, решение по масштабированию воркеров/очередей. Сам `run_agent`
переиспользуется без изменений как единица работы внутри каждой ветки.

## Блок 4 — Генерация PowerPoint

Затрагивает: раздел PowerPoint (11 пунктов).

Нужна библиотека записи `.pptx` + рендеринг графиков (`research-report`
уже закрывает половину с исследованием/текстом). По форме — тот же
sentinel-шаг движка, что уже трижды доказал себя (Code/Video/Audio) —
самый низкий риск среди "настоящей инфраструктуры" блоков.

## Блок 5 — Генерация Excel/дашбордов

Затрагивает: раздел Data Analyzing (10 пунктов).

Нужна библиотека записи `.xlsx` (`financial-report-analyzer`/
`market-research` уже закрывают анализ текстом). Та же форма, что и
PowerPoint-блок.

## Блок 6 — Chatbots как встраиваемый виджет

Затрагивает: раздел Chatbots (10 пунктов).

Собственная функция Knowledge (`knowledge/services.py::search`) уже
*является* RAG-возможностью — не хватает публичного, ограниченного по
частоте запросов эндпоинта + небольшого встраиваемого JS-сниппета.
Меньший блок, чем остальные пять — переиспользует готовую логику,
новое — только публичная поверхность и защита от злоупотреблений.

## Browser Use (14 пунктов) — не отдельный блок

Пересекается с QA-пунктами из App & APIs. Нужен живой браузерный рантайм
на пользователя + решение о хранилище учётных данных (логин/пароль
пользователя к чужому сайту — реальный риск безопасности/ответственности,
требует явного согласия на этот риск, а не только архитектуры). Скорее
всего имеет смысл планировать вместе с блоком 3 (параллельные QA-прогоны)
или блоком 2 (тестирование сгенерированных приложений), когда до него
дойдёт очередь.

`review-sentiment-classifier` (категория «Исследования», единственный

**Фаза B закрыта**: новый sentinel-шаг третьего и четвёртого типа

(зеркалит паттерн `imagegen`/`videogen` — одно приложение на тип

покрытый отдельным тестом. `pitch-deck-builder` (категория «Контент») и
`budget-tracker-builder` (категория «Финансы») — 2 демо-агента. Реальный
smoke-тест через `manage.py shell` подтвердил валидность файлов (слайд с
графиком при валидных данных, корректный пропуск графика при
несовпадающей длине массивов — без падения). Backend 479 тестов, frontend
341 тест + чистые tsc/eslint.
